\noindent\textbf{The rig.}
The vehicle side is an ordinary Android phone and a Jetson Orin Nano, with no
purpose-built hardware (Figure~\ref{fig:architecture}). The phone holds no
interpretation logic. It captures or queries at the rate it is told and forwards
raw data, and every association, fusion and control decision happens on the
Jetson. The phone is tethered through a hotspot rather than carrying its own
subscriber module, because the alternative was a data plan for one experiment.
Two transports are implemented for the same wire protocol. A Tailscale network
is used for development with the phone in hand, and USB is used in the vehicle.
Both devices are powered from the vehicle, so energy is not a binding
constraint.

\noindent\textbf{The sampling controller.}
Each sensor's sampling rate is set at run time by the Jetson and commanded to
the phone. The four rates are camera, GPS, inertial unit and traffic feed. The
costs this controller trades against are traffic-API quota, thermal headroom on
the phone, and Jetson compute. It has two modes. In shadow mode the decision is
recorded and not sent, and in live mode the phone applies it. That distinction
is about sensing configuration only. The rate command carries sampling rates and
a shadow flag, and it never carries driving advice. The word ``live'' in this
paper always describes what the sensing configuration did, and never what the
vehicle did.

\noindent\textbf{The transport.}
One wire protocol serves both links. It carries eight channels, each with its
own sequence numbers, priority, overflow policy and queue depth, over a shared
timebase. The specification is 854 lines, and
\texttt{specs/transport\_golden\_frames.json} pins the frame layout. Both the
Jetson implementation and the phone implementation test against that file rather
than against each other, so neither side can drift by agreeing with the other.

\noindent\textbf{The safety and etiquette gate.}
The advisory passes a filter before it is displayed. The filter is vendored onto
the device from the simulator's safety layer, because the original imports the
simulation stack that the device deliberately does not carry. It holds twelve
rules covering posted limits, minimum front and rear gaps, target-lane
time-to-collision margins, lane-change dwell and rate caps, low-speed
obstruction on an open road, and a bound on how much braking an advisory may
force on a follower. Each rule records, per tick, whether it fired, stayed
quiet, or could not be evaluated at all, with the missing inputs named.
Section~\ref{sec:eval} reports what that census found.

\noindent\textbf{The device cannot drift from what was trained.}
The Jetson must not import the simulator. The contract is therefore vendored:
the field lists, the scales, a NumPy twin of the encoder, the action heads, the
decoders and the neutral fallbacks, pinned to a named simulator commit, with the
export step refusing any dimension mismatch. Vendoring alone is an assertion
rather than a check. What makes it checkable is a frozen file,
\texttt{specs/sim\_contract\_golden\_vectors.json}, holding fourteen encoded
observations, the action schema, both bin decoders and the neutral fallbacks.
Every entry is derived twice, once from the pinned simulator commit and once
from the vendored copy, and the generator refuses to write on any disagreement.
The device-side test reads only the frozen file and imports no simulator module,
so it runs on the Jetson, where the simulator cannot be imported. Regenerating
against the simulator needs a checkout and a deep-learning runtime, so on the
device that step is skipped and only the comparison against the frozen file
runs.

\noindent\textbf{Two design stances.}
The first is to degrade rather than stop. Missing GPS, no camera, no display and
no trained checkpoint each have a defined degraded mode, because debugging time
inside a vehicle is expensive. The second is that the hot path holds no queues,
and the latest value wins. A frame that was never processed is dropped, a slow
display skips ticks, and a stalled card drops log records. For a real-time
advisory, stale data is worse than missing data.

\noindent\textbf{The second runtime.}
The system described so far runs a local-sensing policy, which reads a 39-field
vector built from the camera, GPS and inertial unit. The controller this paper
is about reads the whole network as twelve super-segments of five features, so
it is a separate runtime and was added as one. It loads an exported checkpoint,
refuses any bundle whose network identity does not match the device's own, and
produces a per-super-segment advisory. It reproduces the simulator's own greedy
action exactly on the 185 recorded decisions of the checkpoint's five held-out
seeds, with zero action mismatches and identical Q-values on the exporting
machine. Three deliberately broken runtimes were each seen to fail before that
agreement was trusted. A transposed weight matrix fails to load, two swapped
super-segments are refused at the network fingerprint, and a jam factor drawn
independently of its own formula changes the action on 143 of the 185 decisions.

\noindent\textbf{Scale.}
The phone application is 10{,}501 lines of Kotlin with 17{,}497 lines of Kotlin
tests. The Jetson runtime is 28{,}705 lines of Python with 39{,}027 lines of
tests. The simulator side is 1{,}178 lines, because the environment is a port
and the learner is the published one. Three specification documents total 1{,}138
lines. The repository's test suite is 2{,}702 tests, of which 2{,}678 pass and 24
are skipped.
